# chlift v1.0.0: single-server

chlift moves Postgres event tables into a self-hosted ClickHouse, keeps them in sync with change data capture
(PeerDB), and proves nothing was lost: row counts per day and checksums per primary-key range, on every ClickHouse server.

**v1.0.0 covers ONE server:**
- Postgres → one ClickHouse (with its Keeper on the same host) → PeerDB;
- `chlift install`, `migrate plan`, `migrate start`, `migrate status`, `migrate check` (with `--checksums`),
  `migrate cutover`, `migrate abort`;
- the Prometheus exporter and Grafana dashboard;
- the Go read-side SDK.

## What was tested for this release
- **Single-server fault soak, one 6 h run:** 6.0 h, 35 cycles, 8 injected faults, all applied and verified in
  the containers' own logs (ClickHouse restart, PeerDB worker restart, ClickHouse+Keeper down for 10 minutes,
  Postgres restart).
  - No lost or corrupted rows.
  - Freshness: 0 misses in clean cycles (catch-up p50 5 s, p99 67 s); during the two 10-minute ClickHouse+Keeper outages, ClickHouse missed the 5-minute window and was exact again by the next cycle.
  - Run on a 3-CPU quota on shared cores, with 3 GB for ClickHouse.
  - The memory criterion counts ClickHouse memory-limit errors (Code 241): there were 0. The run's only 2 query
    errors ("no such host", cycle 12) came while our injected outage had ClickHouse stopped, and are graded as
    freshness misses.
  - Criteria fixed before the run: `docs/evidence/single-soak/`.
- **Migration path,** recorded end to end: 14,000,000 rows copied, CDC, checksums 0 of 64 buckets differing, cutover
  in 1 min 52 s (`docs/evidence/numbers.md`).
- **Amazon RDS PostgreSQL 16** (master user): snapshot, CDC and checksums passed.
- **Hosts:** Ubuntu/Debian; Rocky Linux 9 without systemd.

## Requirements
- Postgres 12+ with `wal_level=logical` and `max_slot_wal_keep_size` set. Tables that are updated or deleted must use
  `REPLICA IDENTITY FULL`; `migrate start --apply-postgres` sets it.
- **ClickHouse memory:** 16 GB minimum, 32 GB+ for production (ClickHouse's guidance).
- **CPU:** the soak ran on a 3-CPU quota on shared cores and kept its freshness bar; plan for at least that per server. Add more in proportion to your write rate.
- Docker with compose v2 on the host that runs PeerDB.

## Known limits
- **One server is one point of failure:** losing the host stops replication and queries until it returns. Postgres
  keeps the changes in its replication slot (bounded by `max_slot_wal_keep_size`).
- **Freshness:** ClickHouse catches up within seconds after a ClickHouse or Postgres restart, and by the next 10-minute check after a 10-minute ClickHouse outage. It is not real-time.
- **Mapping:** one Postgres table maps to one ClickHouse table. Joins are not denormalised automatically.
- **Plan carefully:** the sort key and partitioning can't change after the first snapshot (a PeerDB limit).
- **Queries:** updated and deleted tables need `FINAL` in ClickHouse queries while replicating.
- **SDKs:** only Go is available.
- **Not yet tested:** RHEL with systemd; RDS with a non-master user.

## Not part of 1.0
**Replicated layouts** (2+ ClickHouse replicas with a 3-member Keeper) are still preview:
- a 20.4 h soak and a 6 h confirm run lost no rows;
- CPU sizing per mirror is not confirmed yet: at a 2-CPU quota, one freshness miss in 36 cycles.

## Upgrading from v0.1.0-preview
Replace the binary and verify it with `SHA256SUMS`. Existing mirrors keep working. Tested: a mirror created by
v0.1.0-preview was checked, followed through CDC (0 of 64 checksum buckets differing) and aborted cleanly by the new
binary (`docs/evidence/upgrade/`).

## Components in this release
See `docs/releases/versions-v1.0.0.md`: PeerDB, Temporal, SeaweedFS and the Postgres catalog, each with the registry
